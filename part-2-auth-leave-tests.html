Hashing and tokens

One new file holds every cryptographic detail so nothing else has to know them. Think of it as a tiny auth.util.ts.

hr-api/app/core/security.py
from datetime import datetime, timedelta, timezone

import bcrypt
import jwt  # PyJWT

from app.core.config import settings


def hash_password(plain: str) -> str:
    # bcrypt only looks at the first 72 BYTES; we cut explicitly so nobody is surprised.
    return bcrypt.hashpw(plain.encode()[:72], bcrypt.gensalt()).decode()


def verify_password(plain: str, password_hash: str) -> bool:
    return bcrypt.checkpw(plain.encode()[:72], password_hash.encode())


def create_access_token(employee_id: int) -> str:
    expires = datetime.now(timezone.utc) + timedelta(minutes=settings.jwt_expire_minutes)
    payload = {"sub": str(employee_id), "exp": expires}   # PyJWT requires sub to be a string
    return jwt.encode(payload, settings.jwt_secret, algorithm=settings.jwt_algorithm)


def decode_access_token(token: str) -> dict:
    # Raises jwt.PyJWTError (expired, bad signature, malformed) -- callers catch it.
    return jwt.decode(token, settings.jwt_secret, algorithms=[settings.jwt_algorithm])
  • The 72-byte limit. bcrypt ignores everything past byte 72, and bcrypt 4.x does so silently. We truncate on purpose and cap the password at 72 characters in the request schema, so a long passphrase never gives false confidence.
  • sub and exp. Two registered claims are all we need: who the token is about, and when it dies. PyJWT checks exp for you inside decode.
  • Always pass algorithms=[...] on decode. It is a list on purpose; accepting whatever the token header claims is a classic vulnerability.

Why a separate table? The HR record and the login have different lifecycles: someone can be hired before they have a password, and a password can be reset without touching their HR data. SELECT * FROM employees can no longer leak a hash, and making employee_id both primary key and foreign key is what turns this into a real 1:1, because a second credential row for the same person is impossible. An employee with no row simply has no login yet. Compare the shapes in 1:1 vs 1:N vs N:M and read the trade-off in the design decisions.

@router.post("/register", response_model=EmployeeRead, status_code=201)
async def register(body: RegisterRequest, db: DbSession) -> Employee:
    taken = await db.scalar(select(Employee.id).where(Employee.work_email == body.work_email))
    if taken is not None:
        raise HTTPException(status_code=409, detail="Email already registered")
    employee = Employee(
        name=body.name,
        work_email=body.work_email,
        role=Role.EMPLOYEE,                      # never client-controlled
        job_title="New hire",
        date_joined=date.today(),
        salary=0,                                # HR fills this in later
        emp_status=EmploymentStatus.ACTIVE,
    )
    db.add(employee)
    await db.flush()                             # INSERTs the employee so employee.id exists; nothing is committed yet
    db.add(EmployeeCredential(employee_id=employee.id, password_hash=hash_password(body.password)))
    await db.commit()                            # one transaction: both rows land, or neither does
    await db.refresh(employee)
    return employee

The return annotation is Employee (the ORM row) while response_model is EmployeeRead. The handler returns the row; FastAPI filters it through the schema, and the hash is not even a column on that row. More on that in a moment.

POST /auth/login — the one form-encoded endpoint

Why it is not JSON

Everywhere else in this API the body is JSON. Login takes application/x-www-form-urlencoded with fields literally named username and password, because that is the OAuth2 password-flow spec. Following it is what makes the green Authorize button in /docs work: Swagger UI posts exactly this shape to the tokenUrl you declare.

We have no username column, so the form's username carries the email. One endpoint is the exception; the rest stay JSON.

hr-api/app/routers/auth.py
@router.post("/login", response_model=Token)
async def login(
    form: Annotated[OAuth2PasswordRequestForm, Depends()],
    db: DbSession,
) -> Token:
    employee = await db.scalar(select(Employee).where(Employee.work_email == form.username))
    # Employee.credential is joined in, so this is one JOIN query; None means no credential row
    password_hash = employee.credential.password_hash if employee and employee.credential else None
    if password_hash is None or not verify_password(form.password, password_hash):
        # unknown email, no credential row, wrong password: identical 401, nothing to tell them apart
        raise HTTPException(
            status_code=401,
            detail="Incorrect email or password",
            headers={"WWW-Authenticate": "Bearer"},
        )
    return Token(access_token=create_access_token(employee.id))

# new: keyword args → cheatsheet An employee with no credential row fails login exactly like a wrong password, with the same status and message, so the response never reveals whether a person exists or merely has no password. Depends() with no argument means “build the class in the annotation from the request”. FastAPI reads the form fields and hands you an OAuth2PasswordRequestForm instance.

Reading the token: get_current_user

In Express this is the middleware that verifies the header and assigns req.user. Here it is a function whose return value is the user. Add to deps.py:

hr-api/app/deps.py
import jwt
from fastapi import HTTPException
from fastapi.security import OAuth2PasswordBearer

from app.core.security import decode_access_token
from app.models.employee import Employee, EmploymentStatus, Role

oauth2_scheme = OAuth2PasswordBearer(tokenUrl="/auth/login")   # tells /docs where to log in


async def get_current_user(
    token: Annotated[str, Depends(oauth2_scheme)],
    db: DbSession,
) -> Employee:
    unauthorized = HTTPException(
        status_code=401,
        detail="Could not validate credentials",
        headers={"WWW-Authenticate": "Bearer"},
    )
    try:
        payload = decode_access_token(token)
        employee_id = int(payload["sub"])
    except (jwt.PyJWTError, KeyError, ValueError):
        raise unauthorized
    employee = await db.get(Employee, employee_id)
    if employee is None or employee.emp_status == EmploymentStatus.TERMINATED:
        raise unauthorized                      # a valid token for a fired employee is still no
    return employee


CurrentUser = Annotated[Employee, Depends(get_current_user)]

# new: try / except → cheatsheet OAuth2PasswordBearer pulls the token out of Authorization: Bearer ... and answers 401 itself if the header is missing. The WWW-Authenticate: Bearer response header is what the HTTP spec requires on a 401; clients and proxies use it to know a bearer token is the way in.

Roles: require_role, stacked

A function that returns a dependency is how you parameterise one. Add to deps.py:

def require_role(*roles: Role):
    async def checker(user: CurrentUser) -> Employee:

Why this is different

Authorization is a stack of dependencies that raise

Express
app.delete("/employees/:id",
  requireAuth,          // sets req.user (untyped)
  requireRole("hr"),    // reads req.user, calls next(err)
  deleteEmployee);
FastAPI
@router.delete("/{employee_id}",
  dependencies=[HR_ONLY])
async def delete_employee(
    employee_id: int, db: DbSession): ...
# CurrentUser is a typed value, not req.user

A dependency that raises replaces the middleware chain. The difference is not syntax: each link is typed (the handler receives an Employee, not a mutable req), it is declared on the route rather than ordered across a file, and FastAPI reads it when building OpenAPI: OAuth2PasswordBearer puts a lock on every protected route in /docs, and the responses= entries above document the 401 and 403 as part of the contract. A generated TypeScript client, and later an agent, learn the rules from the schema instead of from tribal knowledge.

Field-level filtering: who sees salary

Rule: salary is visible to the owner, the owner's direct manager and any hr_admin. Everyone else gets the same employee without the field. Two schemas, and the route picks:

hr-api/app/schemas/employee.py
class EmployeeReadWithSalary(EmployeeRead):
    salary: int          # annual, whole currency units
hr-api/app/services/employees.py
from app.models.employee import Employee, Role


def can_see_salary(viewer: Employee, target: Employee) -> bool:
    return (
        viewer.id == target.id
        or target.manager_id == viewer.id
        or viewer.role == Role.HR_ADMIN
    )
hr-api/app/routers/employees.py
@router.get(
    "/{employee_id}",
    response_model=None,          # we return the model ourselves
    responses={200: {"model": EmployeeReadWithSalary}},  # documents the richer shape
)
async def get_employee(
    employee_id: int, viewer: CurrentUser, db: DbSession
) -> EmployeeReadWithSalary | EmployeeRead:
    employee = await db.get(Employee, employee_id)
    if employee is None:
        raise HTTPException(status_code=404, detail="Employee not found")
    if can_see_salary(viewer, employee):
        return EmployeeReadWithSalary.model_validate(employee)
    return EmployeeRead.model_validate(employee)

# new: X | Y unions → cheatsheet The list endpoint (GET /employees) keeps returning plain EmployeeRead for everyone; to see a salary you open the individual record, where the rule can be checked against one target. One subtlety worth the three extra lines: EmployeeReadWithSalary subclasses EmployeeRead, so a union response_model would be ambiguous — the richer object validates happily against the narrower member, and salary gets quietly dropped for the very callers allowed to see it. FastAPI also infers response_model from the return annotation, so response_model=None is how you explicitly say I have already built the right model, do not re-validate it. The responses= entry keeps both shapes in /openapi.json for the generated TS client, and the guarantee now comes from the route returning a narrow model rather than from union resolution.

Why filter in the serializer, not in React

If the frontend hides a column, the number has still crossed the network and sits in the response tab for anyone to read. Filtering where the response is built means the forbidden field never leaves the server, and it protects every other consumer too — the next client, a script, the chat agent. UI hiding is cosmetics; this is authorization.

Why this is different

response_model filters the output, so a stray field cannot leak

Express

  const e = await db.employee.find(id);
  res.json(e);   // whatever is on e goes out,
});              // password_hash included

In Express, a field leaks the moment someone adds it to the object and forgets to strip it by hand. In FastAPI the handler returns whatever it likes and the response schema decides what leaves the building: it keeps only the declared fields. The stronger guarantee is structural: password_hash lives in employee_credentials, so it is not in the table being serialised at all, and neither SELECT * FROM employees nor a careless schema edit can leak it. The same mechanism is why the salary rule above is a one-line schema choice, not a scattered delete obj.salary.

Schemas: validation that belongs at the boundary

“End date is not before start date” needs only the request body, so Pydantic enforces it before your code runs. This is the Zod .refine() you would attach by hand in Express, riding on the type.

hr-api/app/schemas/leave.py
from datetime import date
from typing import Annotated, Self

from pydantic import BaseModel, BeforeValidator, ConfigDict, Field, computed_field, model_validator

from app.models.leave import LeaveStatus, LeaveType

# Write by id, read by name: the client sends leave_type_id and gets the "annual" string back
LeaveTypeName = Annotated[str, BeforeValidator(lambda v: v.type if isinstance(v, LeaveType) else v)]


class LeaveRequestCreate(BaseModel):
    leave_type_id: int = Field(examples=[1])
    start_date: date = Field(examples=["2026-12-07"])
    end_date: date = Field(examples=["2026-12-08"])
    reason: str = Field(min_length=1, max_length=500)

    @model_validator(mode="after")
    def end_not_before_start(self) -> Self:
        if self.end_date < self.start_date:
            raise ValueError("end_date must be on or after start_date")
        return self


class LeaveRequestUpdate(BaseModel):
    leave_type_id: int | None = None
    start_date: date | None = None
    end_date: date | None = None
    reason: str | None = Field(default=None, max_length=500)

    @model_validator(mode="after")
    def end_not_before_start(self) -> Self:

Route vs service, one sentence each

The route does HTTP: parse the request, pick a status code, shape the response. The service does rules: who may do what, which transitions are legal, what overlaps. Rules never import fastapi.

404 or 403? A deliberate choice

If you ask for a request you have no business seeing, which do you get? We pick two rules and keep them everywhere:

  • Reading: you may see a request if you own it, you are the owner's direct manager, or you are hr_admin. Anyone else gets 404, so ids cannot be probed to learn what exists.
  • Mutating a request you can see but do not own (a manager trying to cancel an employee's draft): 403. You already know it exists; telling you “no” is honest.

Approvals, and the race

Two endpoints finish the API: approve and reject. They are short. The interesting part is that the obvious way to write approve has a bug that no single request will ever show you.

📌

Storing used_days instead of summing approved requests is the design decision this race is the price of; the trade-off and its alternative are laid out under design decisions, and SQLite's single-writer model is why it bites so sharply.

Who may decide: a guard, not an if

Only the requester's direct manager or an hr_admin may decide, and nobody decides their own request. The rule sits in the service; the route reaches it through a dependency, so the handler body never mentions authorization at all.

The obvious approve

Approving must do two things: mark the request approved, and spend its days from the employee's balance. Read the balance, check it, write it back. Anyone would write this:

Each line is right. The bug is the gap between the check and the write: the number you checked can change before you act on it. A single request never notices. Two overlapping ones do.

The race, on a timeline

Alice has used 8 of 10 annual days. She has two submitted requests: A (2 days) and B (1 day). Her manager approves A while an hr_admin approves B; or one person double-clicks; or an agent fires two tool calls in parallel. Neither request knows the other exists:

With pysqlite's default settings the SELECT is not held inside a transaction, so this interleaving is genuinely possible on SQLite too. (Stricter transaction settings could turn it into a “database is locked” error instead; the logic bug is identical, just louder.)

The fix: one atomic conditional UPDATE

Stop reading and then deciding. Let the database check and write in one statement, and look at how many rows it changed:

(the statement we want the database to run)
UPDATE leave_balances
   SET used_days = used_days + :days
 WHERE employee_id = :employee_id
   AND leave_type_id = :leave_type_id
   AND consumed_year_in = :year
   AND used_days + :days <= entitled_days;
-- rowcount 1: the days were available and are now spent
-- rowcount 0: they were not (or no such balance row); nothing changed
hr-api/app/services/leave.py
async def _debit_balance(db: AsyncSession, req: LeaveRequest) -> None:
    result = await db.execute(
        update(LeaveBalance)
        .where(
            LeaveBalance.employee_id == req.employee_id,
            LeaveBalance.leave_type_id == req.leave_type_id,
            LeaveBalance.consumed_year_in == req.start_date.year,
            LeaveBalance.used_days + req.no_of_days <= LeaveBalance.entitled_days,
        )
        .values(used_days=LeaveBalance.used_days + req.no_of_days)
    )
    if result.rowcount == 0:
        balance = await _find_balance(db, req)      # only to explain the failure; raises if the row is missing
        raise InsufficientBalance(f"Only {balance.entitled_days - balance.used_days} days left")

Replay the timeline (both statements target the same employee, leave type and year): A's statement runs first, finds 8 + 2 <= 10, spends two days, 10 of 10. B's statement then finds 10 + 1 > 10, changes zero rows, and we raise InsufficientBalance (a 409 after chapter 9). The check and the write can no longer be separated because they are the same operation. Press the second button above to see it.

🔑
Why this is the portable fix

It uses nothing but a single SQL statement and the row count, which every relational database makes atomic. It works on SQLite, Postgres and MySQL without caring about locks or isolation levels. Row locks (next box) are another valid answer, but only on databases that have them.

The same idea guards a second race that costs nothing extra: two people approving the same request. We claim the request with a conditional update on request_status before spending anything.

The whole service file, as it stands now

One transaction: the claim, the debit and the commit are a single unit. If the debit raises, we never reach commit(), the session closes, and the claim is rolled back with it. This is the full services/leave.py after chapter 8, ready to compare with your copy.

    await _claim(db, req, LeaveStatus.APPROVED, approver)
    if req.leave_type.type != "unpaid":                # unpaid leave has no balance to spend
        await _debit_balance(db, req)
    await db.commit()                                    # claim + debit land together, or not at all
    await db.refresh(req)
    return req


async def reject(db: AsyncSession, req: LeaveRequest, approver: Employee) -> LeaveRequest:
    await _claim(db, req, LeaveStatus.REJECTED, approver)
    await db.commit()
    await db.refresh(req)
    return req

# new: async / await → cheatsheet # new: keyword args → cheatsheet Status-then-balance order matters: claiming first means the second of two identical approvals fails on the cheap status check and never touches the balance.

What changes under Postgres

Row locks exist there; SQLite does not have them

On Postgres you could keep the read-then-check shape and make it safe by locking the row: SELECT ... FOR UPDATE (in SQLAlchemy, select(LeaveBalance).with_for_update()). The second approval would block on that read until the first commits, then see used_days = 10 and fail the check honestly. Same result, different mechanism.

SQLite has no row locks and no FOR UPDATE. It allows one writer at a time for the whole database file; readers carry on (that is what WAL mode buys you). Writers queue and take turns, which is why the conditional UPDATE above is correct there: each statement runs alone.

This limit is being taught, not hidden. It is also why SQLite is fine for this tutorial and wrong for a busy production API. The conditional UPDATE stays the better habit even on Postgres, because it needs no locks held across a network round trip.

HTTPException, handlers, or Express error middleware?

Express

One mechanism: next(err) or a throw lands in the four-argument error middleware, which you register last and which inspects err to decide a status.

server/app.ts
app.use((err, req, res, next) => {
  const status = err.status ?? 500;
  res.status(status).json({ error: { message: err.message } });
});
FastAPI

The same job split by type: @app.exception_handler(SomeError) registers one function per exception class. No registration order to get wrong, and no next.

HTTPException is simply the built-in exception that already carries a status.

Rule of thumb for this codebase: services raise domain exceptions (no HTTP knowledge); routes and dependencies may raise HTTPException where the concern is HTTP itself, such as the 401 for a bad token; and handlers in main.py convert everything into the one body. Now that the handlers exist, nothing is a plain-text error any more, including the 500.

The chapter 6 and 7 snippets that raised HTTPException(404, ...) from routes still work, because the HTTP handler gives them the same shape. Over time you would move such checks into services as NotFound.

               "content": { "application/json": { "schema": { "$ref": "#/components/schemas/LeaveRequestRead" } } } },
      "403": { "description": "Caller is not the requester's manager or an hr_admin", ... },
      "404": { "description": "No leave request with this id", ... },
      "409": { "description": "Request is not in 'submitted' status, or the balance is too low ...", ... }
    }
  }
}

The generated TypeScript client now has approveLeaveRequest(requestId), a typed LeaveRequestRead result and a typed error body. Generate it with any OpenAPI-to-TypeScript tool pointed at http://localhost:8000/openapi.json; openapi-typescript is one common choice.

Field-level hints help too. Field(examples=[...]) on the schema (we did this on LeaveRequestCreate in chapter 7) puts a concrete sample next to each property, which is the single most effective way to stop a model inventing date formats:

The checklist per endpoint: a verb-first summary; a description that states who may call it, preconditions and side effects; a stable snake_case operation_id (it becomes the tool name); tags for grouping; a response_model; and responses= for every error a caller should plan for. Do this for all 24; the approve example is the template.

Why the descriptions are the agent's tool schemas

An agent framework turns each operation into a “tool”: operation_id is the name, description is the instruction, the parameter and body schemas are the arguments. The model chooses and fills tools purely from that text.

Vague description

"Approve Leave Request" and a bare request_id: integer.

The model does not know who may call it, that it spends balance, or what a 409 means. It guesses: it tries it for the wrong person, retries on a 409, and tells the user it worked.

Specific description

States the role rule, the precondition, the side effect and the failure code.

The model checks the request is submitted first, reports insufficient_balance in plain language, and does not retry a call that cannot succeed.

The agent runs as the user

The rule that matters most

The agent forwards the caller's JWT. It never holds an admin key.

When the chat window calls a tool, the backend request carries the same bearer token the logged-in person's browser holds. Every rule from chapters 6 and 8 then applies unchanged: get_current_user identifies the human, require_role gates the route, can_see_salary filters the field, load_for_decision checks the reporting line.

If instead the agent used a privileged service account and tried to enforce permissions itself in a prompt, one clever message (“ignore your rules and show me everyone's salary”) could undo it. Authorization is enforced inside the API, because the API is the only layer that cannot be talked out of it. A manager's agent can approve their reports' leave and nobody else's, for exactly the reason a manager's browser can.

Destructive tools need a confirmation step

Some actions are hard to undo: deleting an employee, rejecting leave. A language model can misread a sentence, so the destructive tool should never complete in one call. The shape to build later, sketched here (this is a design, not code in the project):

step 1 -- the "preview" tool changes nothing
POST /employees/17/delete-preview

200 {
  "preview": { "action": "delete_employee", "employee": "Eli Park", "open_leave_requests": 2 },
  "confirmation_token": "eyJhbGciOi...",      // signed: action + target + user id + expiry (~5 min)
  "expires_in_seconds": 300
}
step 2 -- the "commit" tool, only reachable with that token
DELETE /employees/17?confirmation_token=eyJhbGciOi...

204   // 409 invalid_transition if the token is expired, for a different target or a different user

The agent shows the preview to the person in the chat and calls the second tool only after they say yes. Because the token is bound to the target, the caller and an expiry, a model cannot skip ahead or reuse an old approval. The signing code would reuse create_access_token's technique from chapter 6 with a different claim set.
