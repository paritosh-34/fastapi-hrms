The one thing worth reading before you start

Python's type annotations are, almost everywhere, exactly as real as TypeScript's: erased, unchecked, decoration for your editor. def f(x: int) happily accepts "nope" and nothing complains.

FastAPI and Pydantic break that rule on purpose. They read your annotations at runtime with typing.get_type_hints and use them to parse, coerce and reject incoming data. So in the tutorial, a type hint is not a comment — it is the validator, the parser, and the OpenAPI schema all at once. That one inversion is why FastAPI feels different from Express, and it is the reason this sheet spends more space on section 9 than on anything else.

Section 1

Values and collections

Four container types do all the work: dict, list, tuple, set. The first two are your object and array; the other two you will meet in passing.

Objects → dict keys · access · merge · spread #dicts
JavaScript
const emp = {
  name: "Priya",
  role: "manager",
};

emp.name;          // "Priya"
emp["role"];      // "manager"
emp.missing;       // undefined
emp.title ?? "—";  // fallback

const merged = { ...emp, role: "hr_admin" };
Object.keys(emp);
"name" in emp;      // true
Python
emp = {
    "name": "Priya",
    "role": "manager",
}

emp["name"]            # "Priya"
emp["role"]            # "manager"
emp["missing"]         # 💥 KeyError
emp.get("title", "—")   # fallback

merged = {**emp, "role": "hr_admin"}
list(emp.keys())
"name" in emp           # True

The one that will bite you: there is no undefined. Reading a key that is not there raises KeyError instead of returning a blank. Use .get(key) for None, or .get(key, default) for a fallback. Also: keys are quoted strings, so there is no dot access — emp.name on a dict is an AttributeError.

Arrays → list push · slice · len · sort #lists
JavaScript
const ids = [3, 1, 2];

ids.push(4);
ids.length;        // 4
ids[0];
ids.at(-1);         // last
ids.slice(0, 2);
[...ids, 9];
ids.includes(2);
ids.sort((a,b) => a-b);
ids.join(",");
Python
ids = [3, 1, 2]

ids.append(4)
len(ids)             # 4
ids[0]
ids[-1]              # last — negative index!
ids[0:2]
[*ids, 9]
2 in ids
ids.sort()           # in place, numeric by default
",".join(str(i) for i in ids)

Three differences worth memorising: len(x) is a function, not a property, and it works on lists, dicts, strings and sets alike. Negative indexing is built in, so ids[-1] is the last item. And .sort() sorts numbers correctly out of the box — none of the [1,10,2] lexicographic nonsense — but it mutates and returns None; use sorted(ids) for a new list.

tuple — a fixed-length, immutable list unpacking · multiple return #tuples
JavaScript
// no real equivalent — an array you
// promise not to mutate
const pair = ["start", "end"];
const [a, b] = pair;

// returning two things
function range() { return [1, 30]; }
const [lo, hi] = range();

// TS: readonly [string, string]
Python
pair = ("start", "end")
a, b = pair          # unpacking

# returning two things
def date_range() -> tuple[int, int]:
    return 1, 30      # parens optional

lo, hi = date_range()

pair[0] = "x"        # 💥 TypeError

You will mostly meet tuples as “this function returns two values” and as the thing a, b = ... unpacks. In the API build they show up as the return of a service function (return request, balance) and as the type tuple[int, int].

set — unique membership dedupe · overlap · in #sets
JavaScript
const roles = new Set(["hr", "hr", "mgr"]);
roles.has("hr");
roles.size;

// intersection: by hand
[...a].filter(x => b.has(x));
Python
roles = {"hr", "hr", "mgr"}   # 2 items
"hr" in roles
len(roles)

# set algebra is built in
a & b   # intersection
a | b   # union
a - b   # difference

Note the collision: {} is an empty dict, not an empty set. An empty set is set(). In the build, sets appear when we check whether a requested leave range overlaps the days already booked.

None — the only empty value null · undefined · is None #none
JavaScript
// two empties, and you check for both
let x = null;
let y;              // undefined

if (x == null) {}    // catches both
x ?? "fallback";
obj?.deep?.key;
Python
# one empty value, full stop
x = None

if x is None: ...      # always `is`, not ==
if x is not None: ...

x or "fallback"        # ⚠️ also fires on 0 and ""
# no ?. operator — guard explicitly
dept.name if dept is not None else None

No optional chaining. There is no ?. and no ??. The idiom is an explicit if ... is None guard, or the inline conditional shown above. And always compare with is None rather than == None — for ordinary values they agree, but == can be overridden by a class, and SQLAlchemy in particular overloads it to build SQL, where column == None produces IS NULL rather than a boolean.

Strings

Template literals → f"..." f-string · interpolation #fstrings
JavaScript
const name = "Priya", days = 3;

`${name} booked ${days} day`;
`total: ${(d * 1.5).toFixed(2)}`;

// multi-line: backticks
`line one
line two`;
Python
name, days = "Priya", 3

f"{name} booked {days} day"
f"total: {d * 1.5:.2f}"   # format spec

# multi-line: triple quotes
"""line one
line two"""

f"{emp['name']}"   # inner quotes must differ

The f prefix is mandatory — without it you get the literal text {name}, which is the single most common Python typo for a JS developer. Bonus: the colon format spec (:.2f, :,, :>8) replaces toFixed and padStart.

String methods, renamed trim · split · lower · in #strops
JavaScript
s.trim()
s.toLowerCase()
s.toUpperCase()
s.includes("@")
s.startsWith("HR-")
s.split(",")
s.replaceAll("-", "_")
s.length
Number(s)  // may give NaN
Python
s.strip()
s.lower()
s.upper()
"@" in s           # operator, not method
s.startswith("HR-")  # all lowercase
s.split(",")
s.replace("-", "_")  # replaces ALL
len(s)
int(s)            # 💥 ValueError if not a number

Method names are snake_case or just squashed (startswith, not startsWith). There is no NaN escape hatch: int("abc") raises instead of producing a poisoned value — which is a big part of why Pydantic can give you a clean 422 instead of a NaN leaking into your database.

Loops and comprehensions

Python has one loop you will ever write: for x in thing. What replaces .map() and .filter() is a comprehension — the same operation with the brackets on the outside.

.map / .filter → comprehensions list · dict · generator #comprehensions
JavaScript
emps.map(e => e.name)

emps.filter(e => e.active)

emps.filter(e => e.active)
    .map(e => e.name)

Object.fromEntries(
  emps.map(e => [e.id, e])
)

emps.some(e => e.active)
emps.every(e => e.active)
emps.reduce((a,e) => a+e.days, 0)
Python
[e.name for e in emps]

[e for e in emps if e.active]

[e.name for e in emps if e.active]


{e.id: e for e in emps}   # dict comprehension



any(e.active for e in emps)
all(e.active for e in emps)
sum(e.days for e in emps)

Read it right-to-left-ish: [ what I want for each item if condition ]. The square brackets make a list; curly braces with a key: value make a dict; plain parentheses (or no brackets at all, inside a function call) make a lazy generator.

Chaining is flat rather than nested — one comprehension with both a for and an if replaces .filter().map(). And any, all, sum, min, max are built-ins that take a generator, which covers almost every reduce you have ever written.

Iterating with an index or over a dict enumerate · items · range · zip #forloops
JavaScript
for (const e of emps) {}

emps.forEach((e, i) => {});

for (const [k, v] of Object.entries(o)) {}

for (let i = 0; i < 5; i++) {}

a.map((x, i) => [x, b[i]]);
Python
for e in emps:
    ...

for i, e in enumerate(emps):
    ...

for k, v in o.items():
    ...

for i in range(5):   # 0,1,2,3,4
    ...

for x, y in zip(a, b):
    ...

Looping over a dict gives you its keys, not its values — use .items() for pairs and .values() for values. range(start, stop) excludes stop, exactly like Array.slice. In chapter 7 we use range plus a date step to count working days in a leave request.

The classic counting loop range · i++ · ids[i] · len #rangeloop
JavaScript
const ids = [10, 20, 30, 40];

for (let i = 0; i < 4; i++) {
  console.log(`Element at ${i} is ${ids[i]}`);
}

// bound by length, not a magic number
for (let i = 0; i < ids.length; i++) {
  console.log(ids[i]);
}
Python
ids = [10, 20, 30, 40]

for i in range(0, 4):
    print(f"Element at {i} is {ids[i]}")


# bound by length, not a magic number
for i in range(len(ids)):
    print(ids[i])

# but this is what you actually want:
for i, v in enumerate(ids):
    print(f"Element at {i} is {v}")

There is no three-part loop header and no i++. range carries all three parts instead: range(stop), range(start, stop), range(start, stop, step). stop is always excluded, so range(0, 4) gives 0, 1, 2, 3 — and because start defaults to 0, range(0, 4) and range(4) are the same thing.

The hardcoded 4 is the usual bug: shrink ids and you get an IndexError rather than JS's undefined, which fails loudly in a request handler. range(len(ids)) is the literal translation, but reach for enumerate whenever you want the index and the value — you only really need a bare range when you are counting something other than list positions, like stepping a date forward one day at a time.

One formatting note, since this is probably your first hand-typed Python block: indent the body with 4 spaces, not a tab. Mixing the two is an IndentationError — see #gotchas.

Truthiness, booleans and equality

Truthiness and the logical operators True · and · or · not · === #truthiness
JavaScript
true / false
a && b
a || b
!a

a === b        // strict
a == b         // coercing — avoid

// falsy: 0 "" null undefined NaN
if (list.length === 0) {}
if (Object.keys(o).length === 0) {}
// [] and {} are TRUTHY
Python
True / False        # capitalised!
a and b
a or b
not a

a == b         # there is no ===
a is b         # same object, not same value

# falsy: 0 "" None [] {} set() 0.0
if not my_list: ...
if not my_dict: ...
# empty containers ARE falsy

Two flips to internalise. First, == is the safe one here — Python does not coerce across types, so 1 == "1" is simply False and there is no === to reach for. is means identity, and using it for value comparison is a real bug (x is 300 can be False); reserve it for None, True and False.

Second, empty lists and dicts are falsy, which is the opposite of JS. So if not results: is the idiomatic “nothing came back” check, and you no longer need .length === 0.

Functions

function → def def · lambda · return type #functions
TypeScript
function raise(salary: number,
               pct: number): number {
  return salary * (1 + pct / 100);
}

const double = (x: number) => x * 2;

// no explicit return -> undefined
Python
def raise_salary(salary: float,
                 pct: float) -> float:
    return salary * (1 + pct / 100)


double = lambda x: x * 2   # rarely used

# no explicit return -> None
def log(msg: str) -> None:
    print(msg)

The return type goes after ->. A function that returns nothing is annotated -> None. lambda is a crippled arrow function — single expression only, no statements — so idiomatic Python uses a named def almost everywhere, and you will barely see lambda in this tutorial outside of a sort(key=...).

The options object → keyword arguments named args · defaults · *args **kwargs #kwargs
TypeScript
// you fake named args with an object
function list({ limit = 20, offset = 0,
                search }: Opts) {}

list({ search: "pri", limit: 5 });

// rest params
function tag(...names: string[]) {}
Python
# named args are native
def list_employees(limit: int = 20,
                   offset: int = 0,
                   search: str | None = None): ...

list_employees(search="pri", limit=5)  # any order

# *args = rest, **kwargs = rest-of-object
def tag(*names: str, **extra: str): ...

This is the feature FastAPI is built on. Because every parameter is independently named, typed and defaultable, FastAPI can look at a function signature and decide for itself which arguments come from the path, which from the query string, which from the body, and which are dependencies — no options object, no req.query digging. Keep this row in mind when you reach Depends.

Modules and imports

ESM imports → Python imports from · import · no export #imports
JavaScript
import express from "express";
import { Router } from "express";
import { Router as R } from "express";
import { db } from "./db.js";
import { x } from "../core/x.js";

// and you must export
export const db = ...;
Python
import fastapi
from fastapi import APIRouter
from fastapi import APIRouter as R
from app.db import get_db     # no ./ no .py
from app.core.config import settings

# nothing to export — every top-level
# name in the file is importable
db = ...

No export keyword. Every module-level name is public by convention; a leading underscore (_internal) is the only privacy marker and it is advisory. Paths use dots instead of slashes, never include .py, and are resolved from where you launched the process — which is why the tutorial always runs uvicorn app.main:app from the project root, and why a folder becomes a package once it contains an __init__.py (empty is fine).

One real trap: circular imports are a runtime crash, not a warning. Chapter 5 lays the package out specifically to avoid them — models never import routers.

Classes, just enough

You will not write much OO in this build, but you will read classes constantly: every Pydantic schema and every SQLAlchemy model is a class body full of annotated attributes.

class, constructor and this __init__ · self · inheritance #classes
TypeScript
class Employee {
  name: string;
  constructor(name: string) {
    this.name = name;
  }
  greet() {
    return `hi ${this.name}`;
  }
}

class Manager extends Employee {}
new Employee("Priya");
Python
class Employee:
    def __init__(self, name: str) -> None:
        self.name = name

    def greet(self) -> str:
        return f"hi {self.name}"


class Manager(Employee):      # inheritance
    pass

Employee("Priya")                # no `new`

self is this, except it is an explicit first parameter on every method — which is verbose but means self can never be rebound by how you call the function, so none of JS's this-binding puzzles exist. There is no new. pass is the “empty block” placeholder, since whitespace alone cannot express an empty body.

A type/interface → a model class BaseModel · dataclass · Mapped #dataclass
TypeScript
interface EmployeeCreate {
  name: string;
  email: string;
  salary?: number;
}

// to validate at runtime you reach
// for a second tool:
const Schema = z.object({
  name: z.string().min(1),
  email: z.string().email(),
});
Python
from pydantic import BaseModel, EmailStr, Field

class EmployeeCreate(BaseModel):
    name: str = Field(min_length=1)
    email: EmailStr
    salary: float | None = None

# the class IS the validator.
# no second schema to keep in sync.
EmployeeCreate(name="", email="x")
# 💥 ValidationError, 2 problems

This is the row the whole tutorial leans on. In TypeScript, your interface and your Zod schema are two declarations of the same shape that drift apart. In Python, a Pydantic class is both at once: the editor reads it for autocompletion and Pydantic reads it at runtime to validate. You will also see plain @dataclass (no validation, just a shape) and SQLAlchemy's Mapped[str] (a shape that maps to a database column) — same idea, three flavours.

Errors

try/catch → try/except raise · except · finally · custom #tryexcept
JavaScript
try {
  risky();
} catch (err) {
  if (err instanceof TypeError) {}
  throw new Error("wrapped");
} finally {
  cleanup();
}

class NotFound extends Error {}
Python
try:
    risky()
except ValueError as err:        # typed catch
    raise RuntimeError("wrapped") from err
except (KeyError, IndexError):
    ...
finally:
    cleanup()

class NotFound(Exception):
    pass

You can catch by type directly — except ValueError: instead of catching everything and then testing with instanceof. Several except clauses are tried in order, so put the specific ones first. raise X from err preserves the original cause in the traceback.

Bare except: swallows absolutely everything including Ctrl-C; if you must catch broadly, write except Exception:. Chapter 9 defines domain exceptions this way (LeaveOverlap, InsufficientBalance) and maps each to an HTTP status in one place.

The annotations you'll type

Everything in this section has a TypeScript twin you already use daily. The difference is not the syntax, it is that FastAPI reads these at runtime.

Unions and nullables: str | None union · optional · Optional #optional
TypeScript
name: string | null
id: string | number
dept?: string      // optional key

// optional ≠ nullable in TS
Python
name: str | None
id: str | int
dept: str | None = None   # optional ⇒ has a default

# older style, same meaning:
from typing import Optional
name: Optional[str]

X | None is the modern spelling and what the tutorial uses; Optional[X] is the identical older one you will meet in blog posts. Important for FastAPI: the annotation alone makes a field nullable; what makes it optional in the request is the = None default. A field annotated str | None with no default is still required — you just have to pass null explicitly.

Collections: list[int], dict[str, float] generics · Array<T> · Record #generics
TypeScript
ids: number[]
ids: Array<number>
byId: Record<string, Employee>
pair: [number, number]
rows: Employee[][]
Python
ids: list[int]
# (same thing — one spelling only)
by_id: dict[str, Employee]
pair: tuple[int, int]
rows: list[list[Employee]]

Square brackets do what angle brackets do in TS. Lowercase list/dict/tuple are correct on modern Python; the capitalised List/Dict from typing are the deprecated old spelling. When a route is annotated -> list[EmployeeRead], FastAPI both serialises each item through that schema and publishes an array schema in /openapi.json.

String-literal unions: Literal[...] Literal · "a" | "b" #literal
TypeScript
type Role = "employee" | "manager"
            | "hr_admin";

function f(sort: "asc" | "desc") {}
Python
from typing import Literal

Role = Literal["employee", "manager", "hr_admin"]

def f(sort: Literal["asc", "desc"] = "asc"): ...

Identical idea, comma instead of pipe. Annotate a query parameter with a Literal and you get three things for free: editor autocompletion, a 422 rejection of anything else, and a dropdown of the valid values in /docs. This is the cheapest validation in the whole framework.

Real enums: class Role(str, Enum) Enum · StrEnum #enums
TypeScript
enum Role {
  Employee = "employee",
  Manager  = "manager",
  HrAdmin  = "hr_admin",
}

Role.Manager;         // "manager"
Python
from enum import Enum

class Role(str, Enum):
    EMPLOYEE = "employee"
    MANAGER  = "manager"
    HR_ADMIN = "hr_admin"

Role.MANAGER.value    # "manager"
Role("manager")       # parse from string

Why inherit from str as well as Enum? Because then a Role member is a string: it compares equal to "manager", serialises to JSON as "manager", and goes into a SQLite column without conversion. Without the str base you get <Role.MANAGER: 'manager'> leaking into your responses.

Use Literal for a throwaway set of query-parameter values; use an Enum when the same set is referenced in models, services and tests — as Role and LeaveStatus are throughout this build.

Annotated[T, ...] — a type plus instructions Annotated · Depends · Query #annotated
TypeScript
// no equivalent. The closest thing is
// a branded type plus a decorator, or
// metadata you keep somewhere else:

type PageSize = number;  // 1..100?
// …enforced in a separate Zod schema
// …documented in a separate comment
Python
from typing import Annotated
from fastapi import Query, Depends

# "an int, AND here is what to do with it"
PageSize = Annotated[int, Query(ge=1, le=100)]

def list_employees(
    limit: PageSize = 20,
    db: Annotated[AsyncSession, Depends(get_db)],
): ...

Annotated[T, extra] means “the type is T, and here is extra baggage for whoever cares”. Type checkers ignore the baggage; FastAPI reads it. That one mechanism is how a parameter gets constraints (Query(ge=1)), a description for the OpenAPI schema, or an injected dependency (Depends(get_db)) without inventing new syntax.

It is also how you give a named alias to a repeated dependency — CurrentUser = Annotated[Employee, Depends(get_current_user)] — so a route signature reads user: CurrentUser instead of twenty characters of plumbing. Chapter 6 does exactly this.

Are these checked at runtime? Mostly no. erased · mypy · the exception #typing-erased
TypeScript
// erased at build time
function f(x: number) { return x; }
f("nope" as any);   // runs fine

// so you add Zod at the boundary
Schema.parse(req.body);
Python
# also erased — nothing enforces this
def f(x: int) -> int: return x
f("nope")        # runs fine, returns "nope"

# EXCEPT where a library reads them:
EmployeeCreate(**payload)   # validates
@app.post("/employees")        # validates

Treat annotations as documentation that your editor and mypy enforce before you run, exactly like TS. The exception is the entire reason this tutorial exists: at the HTTP boundary, FastAPI and Pydantic promote your annotations to real runtime validation, so the Zod step disappears and the schema can never drift from the handler.

async — nearly identical, one real trap

async/await and Promise.all coroutine · gather · event loop #asyncawait
JavaScript
async function load(id) {
  const e = await db.find(id);
  return e;
}

await Promise.all([a(), b()]);

// calling it without await gives
// you a pending Promise
const p = load(1);
Python
async def load(id: int) -> Employee:
    e = await db.get(Employee, id)
    return e


await asyncio.gather(a(), b())

# calling it without await gives you a
# coroutine that never runs (+ a warning)
c = load(1)

Same keywords, same single-threaded event loop, same rule that await only works inside an async def. asyncio.gather is Promise.all. The one behavioural difference: a Python coroutine is lazy — it does nothing at all until awaited, whereas a JS promise starts executing the moment you create it.

⚠️ The trap: a blocking call inside async def blocking · requests · time.sleep #blocking
JavaScript
// you can barely do this by accident:
// the whole ecosystem is async, and
// there is no sync HTTP client to
// reach for in the first place.

// fs.readFileSync is the rare case —
// and you already know it's bad.
Python
# every library has a sync version, and
# pip install will happily give it to you

async def handler():
    r = requests.get(url)    # 💥 blocks EVERY request
    time.sleep(1)            # 💥 freezes the server

async def handler():
    async with httpx.AsyncClient() as c:
        r = await c.get(url)   # ✅
    await asyncio.sleep(1)        # ✅

This is the single most expensive mistake in a FastAPI codebase, and chapter 3 gets a full callout for it. Because Python's libraries all have a synchronous flavour, it is easy to pip install requests and drop it into an async def — where it blocks the event loop and serialises every concurrent request behind it.

The rule: inside async def, every I/O call must be awaited (httpx, not requests; aiosqlite, not sqlite3; asyncio.sleep, not time.sleep). If you are stuck with a blocking library, the escape hatch is to declare the route as plain def instead of async def — FastAPI then runs it in a worker thread, which is safe, just not concurrent in the same way.

Decorators and the shell

@decorator @app.get · wrapper #decorators
TypeScript
// you've seen these in TS
@Component({ ... })
class Thing {}

// a decorator is a function that
// receives what's below it
Python
@app.get("/employees")
async def list_employees(): ...

# identical to:
async def list_employees(): ...
list_employees = app.get("/employees")(list_employees)

Exactly what you expect from TS decorators: a function that takes the thing below it and registers or wraps it. @app.get("/path") is Express's app.get("/path", handler) with the handler moved to the next line. Nothing more to learn here.

npm → pip, node_modules → venv venv · pip · requirements.txt · uv #venv
Terminal · Node

The shape is the same, with one extra step. Operators and small syntax ternary · // · no ++ · chaining #misc-ops
JavaScript

Math.floor(a / b)

// comments

Section 12 · come back when something breaks

The gotchas that actually bite

Not a list of trivia. These are the six errors a JS developer hits in their first week of Python, with the fix.

␣Indentation is the syntax

There are no braces. A block is whatever is indented under the :, and mixing tabs with spaces is an IndentationError. Nothing is optional about it.

Fix: 4 spaces, let your editor insert them, never tabs
🔑dict["k"] raises

Missing keys do not give you undefined — they raise KeyError and return a 500. The same goes for list[9] on a short list (IndexError).

Fix: d.get("k"), or d.get("k", default)
🧨Mutable default arguments

def f(items: list = []) creates that list once, at import, and every call shares it. Append in one request, see it in the next. A genuinely confusing bug.

Fix: items: list | None = None, then items = items or []
🅣True, not true

True, False, None are capitalised. Lowercase true is just an undefined variable name, so you get NameError rather than a syntax error.

Fix: muscle memory. The error message is clear.
≡No ===, and is isn't it

== is already strict. is compares identity and appears to work on small numbers and short strings because of interning, then fails on bigger ones.

Fix: == for values, is only for None/True/False
🧵Blocking I/O in async def

The expensive one. A sync library inside an async route stalls the entire server, and nothing warns you — the app just stops scaling.

Fix: see #blocking
🐚Forgetting to activate the venv

ModuleNotFoundError for a package you are certain you installed. You installed it — into a different environment, or globally.

Fix: source .venv/bin/activate, check for (.venv)
🔁Circular imports crash

Two modules importing each other is a hard ImportError at startup, not a resolved cycle. Common once you split routers from models.

Fix: one-way layering — routers → services → models
